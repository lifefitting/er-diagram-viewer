# DB ER Diagram Viewer — 产品介绍

> **一句话定位**：把 `CREATE TABLE` 直接粘进浏览器，秒级出 ER 图；缺外键？它替你猜。

---

## 一、它解决什么问题

数据库 review、新成员 onboarding、跨团队对齐、写设计文档——这些场景反复出现同一个痛点：

- 手边的 ER 图工具要么**重**（要装 client、连数据库）、要么**学习成本高**（dbdiagram.io 自有 DSL）、要么**贵**（drawSQL 等 SaaS 商业产品）；
- 而手边只有一份 `schema.sql`，且常常**没写 FOREIGN KEY**——大多数公司线上库都关了 FK 约束以追求性能；
- 即便愿意手画，画了也没人维护，下次改完表又过时。

**DB ER Diagram Viewer** 的设计原则就一句话：

> 用户拥有的输入只有 SQL DDL，工具要做的事就是 5 秒内变出能用的 ER 图，并把 SQL 里没写明、但语义上明显存在的关系给找回来。

## 二、核心特性

### 1. 零门槛：粘贴即用

- **纯浏览器单页应用**，无需注册、无需登录、无需后端。
- 直接打开网页 → 粘贴 SQL → 立刻成图。
- 离线可用，刷新自动还原（基于 localStorage 持久化）。
- 不上传 SQL 到任何服务器，**敏感 schema 不出本地**。

### 2. 智能 FK 推断（核心差异化能力）

绝大多数线上 MySQL 库为了性能并不真正声明 `FOREIGN KEY` 约束。本工具能基于：

| 维度 | 启发式规则 |
|---|---|
| **命名约定** | `xxx_id` / `xxxId` 列默认指向 `xxx` 或 `xxxs` 表 |
| **类型兼容** | 源列与目标主键的归一化类型必须一致（`int` / `string` / `uuid` 等） |
| **索引信号** | 源列建了索引则置信度更高 |
| **前缀归一** | `t_user` / `tbl_user` / `users` / `user` 自动视作同一目标 |
| **复合前缀兜底** | `parent_user_id`、`created_by_user_id` 也能匹配到 `user` 表 |

产出 **高 / 中 / 低** 三档置信度的候选 FK，每条都附"为什么"的推断理由。

### 3. 模块自动着色

按表名前缀 + FK 邻接关系，自动把表归类为业务"模块"（如 `user / order / inventory / marketing`），并分配独立色彩。让一个 50+ 表的 schema 一眼能看出"哪些表是一伙的"。

提供四套调色板：

| 配色 | 适用场景 |
|---|---|
| **鲜艳 (Vibrant)** | 演讲、答辩、有投影 |
| **粉彩 (Pastel)** | 长时间阅读、设计文档配图 |
| **大地 (Earth)** | 杂志/出版物风格 |
| **单色 (Mono)** | 打印输出、黑白复印 |

### 4. 分片合并

按月/日/分区/分桶命名的物理表会自动合并为单一逻辑节点：

```
account_detail_202401
account_detail_202402   →  account_detail_*  （shards: 4）
account_detail_202403
account_detail_202404
```

支持的命名模式：`_YYYYMM`、`_YYYYMMDD`、`_YYYY_MM_DD`、`_pN`、`_shardN`、`_partN`、纯数字尾缀。**这是国内业务库 review 的高频痛点**——很多 schema 里 80% 的 noise 都是分表。

### 5. 可交互的 ER 画布

- **两种布局**：力导向（fcose）/ 分层（dagre），一键切换。
- **拖拽自由调整**：节点位置、卡片宽度均可调，位置保存在本地。
- **per-field 边路由**：FK 连线精准对接到具体列行（不是粗放地连到表卡片边缘）。
- **Hub 雷达布局**：≥3 入度的"枢纽表"，其下游会自动排成圆环，字母序顺时针——再多的依赖也能逐个扫一遍。
- **三态高亮**：搜索 / 焦点 / 邻居关系下，画布自动突出相关表与边、淡化其余。
- **表折叠**：每个表可单独折叠为表头，节省 80% 屏幕空间。

### 6. 人工确认 + 决策持久化

- 推断面板里每条候选 FK 可"接受 / 拒绝"，决策实时反映到画布（虚线→实线 / 消失）。
- 决策保存在 localStorage，下次打开继续工作。
- 提供"批量接受 / 批量拒绝 / 清除决策"等批操作。

### 7. 多格式导出

| 格式 | 用途 |
|---|---|
| **PNG (2x)** | 文档配图、PPT、答辩截图 |
| **SVG** | 矢量、可二次编辑、嵌入设计稿 |
| **含 FK 的 DDL** | 在原 SQL 末尾追加 `ALTER TABLE ADD CONSTRAINT`，可直接回写到代码库 |

DDL 导出是真正"闭环"的能力：你 review 完一份没有 FK 的脚本，可以**导出一份补全了 FK 的 SQL**作为新版 schema 提交。

## 三、典型使用场景

### 场景 A：新人 onboarding

> "我刚加入这家公司，被甩了 200 张表的 schema.sql，让我一周内熟悉。"

1. 粘贴 → 立即看到模块化着色的 ER 图。
2. 点击 `user` 模块色块 → 画布平滑居中到 user 相关 20 张表。
3. 点击 `users` 表卡片 → 高亮所有指向 users 的 FK，看到它是中心枢纽。
4. 折叠不重要的模块 → 屏幕只留核心 5 个模块。
5. 导出 PNG 作为入职笔记。

### 场景 B：DB 设计 review

> "实习生交了一份新业务表的 DDL，想看它是否和现有库设计兼容。"

1. 把现有库 + 新表的 DDL 一起粘进来。
2. 推断 FK 面板自动列出新表与现有表的关联候选。
3. 逐条 review：哪些是预期的、哪些是命名巧合（如 `created_by` 实际指向 `users`，是合理的；`status_id` 推断到 `statuses` 表是误推断，拒绝）。
4. 导出"含 FK 的 DDL"，把通过的推断作为正式约束建议回写。

### 场景 C：跨团队对齐

> "前后端开会要对一下'订单'这块的数据流，PM 没有 ER 图。"

1. 现场粘贴本地 DDL。
2. 搜索 `order` → 画布只剩订单相关的 8 张表 + 它们的 FK 邻居。
3. 屏幕分享给整个会议 → 直接对着画布讨论。

### 场景 D：分库分表系统 review

> "我们的 user_log 按天拆，有 800 张物理表，怎么看？"

1. 粘贴包含 `user_log_20240101` 至 `user_log_20240801` 的 DDL。
2. 工具自动合并为单一 `user_log_*` 节点，徽标显示"shards: 213"。
3. 干净的画布上只剩 30 个逻辑节点，立即可读。

## 五、技术与轻量性

- **构建产物 ~268 KB gzip**，单文件可直接静态托管或本地双击 `dist/index.html` 离线运行。
- **技术栈极简**：React 18 + TypeScript + Vite + Tailwind + Cytoscape.js + Zustand，无后端，无依赖外部 CDN。
- **TypeScript strict 模式全开**，类型即文档。
- **核心解析与推断带单元测试**，关键路径回归有保障。

## 六、已知限制

诚实的产品也得说清楚边界：

1. **不支持视图 / 触发器 / 存储过程**：DDL 范围限于 `CREATE TABLE / ALTER TABLE / CREATE INDEX`。
2. **PG `COMMENT ON TABLE/COLUMN ... IS '...'` 暂不解析**：可用 inline `COMMENT '...'` 或 MySQL 表级 `COMMENT='...'` 替代。
3. **复合主键的表不会作为 FK 推断的目标**：解析能识别，但推断引擎当前只针对单列 PK 的表。
4. **无云端协作**：分享需手动导出 PNG/SVG/DDL；如需要"复活"上次状态只能在同一浏览器。
5. **超大 schema (200+ 表) 上首次布局可能 5-10s**：建议在大 schema 上预设 dagre 分层布局。

详细路线图参见 [`CODE_REVIEW.md`](./CODE_REVIEW.md) 第七节。

## 七、产品哲学

我们做了这些刻意的取舍：

1. **不做 SQL DSL** —— 用户的 schema 已经是 SQL，再让他们翻译成另一种 DSL 就是给中间商抽税。
2. **不做云端** —— 数据库 schema 是公司核心资产，让它出本地浏览器是个 deal breaker。
3. **不做"完美 SQL parser"** —— 90% 的 DDL 子集已经够用，剩下 10% 边角语法（PG 数组、`GENERATED ALWAYS`、`COLLATE`...）等真有用户反馈再加。轻量优先。
4. **做隐式 FK 推断** —— 这是国内业务库的真实场景：FK 没声明、但语义上明显存在。一个工具能做对这件事，就值得用。
5. **做分表合并** —— 国内业务库的第二真实场景：分库分表把视图弄得一片狼藉。
6. **做模块着色** —— 让 50 张表的 schema "一眼能扫"，而不是变成一张密密麻麻的蜘蛛网。

## 九、上手三步

```bash
git clone <repo>
cd er-diagram-viewer
npm install && npm run dev
```

打开 `http://localhost:5173`，首屏就是一个电商样例 schema（13 表 + 分表）。

不想本地跑？直接 `npm run build && npm run preview` 后把 `dist/` 静态托管到任何地方（GitHub Pages / Vercel / 公司内网静态服务器），全员可访问。
