# Roadmap — 下一步价值挖掘计划

> 定位：**DB 设计评审工具**，不只是画图工具。
> 当前闭环：SQL → ER 图（缩放/布局/推断）→ 关系确认（外键 / 逻辑关联 / 手动连线）→
> 字段批注 → 评审报告 + 数据库说明文档导出。
> 本文按「对评审工作流的价值」排序，分四个阶段；每项标注价值、做法要点、工作量粗估与依赖。
> 更新时间：2026-08-01（v0.3.5 基线）。已完成事项保留为产品决策依据，推荐顺序只针对未完成事项。

## 阶段一：让评审结论"流转起来"（最高价值，直接延伸闭环）

### 0.3.5 已纳入基线

工作区存档、密码保护、多工作区合并、结构化批注、表删除决策、标准数据库说明书、
布局精调、字段顺序持久化、模块批量调整、增量 SQL 续编保护和画布右键快控均已进入
当前版本，不再作为下一阶段任务重复排期。

### 1.1 工作区存档 / 导入 ✅ 已完成（2026-07-12，feat/workspace-archive）

- **实现**：按原方案落地——`.erreview` = 持久化快照 + 版本元信息
  （[src/exports/archive.ts](src/exports/archive.ts)）；导入复用 `sanitizePersisted`
  逐字段校验，persistVersion 不兼容降级仅 rawSql，`parseSql` 预检保护当前工作区；
  应用侧 `importWorkspace` + `workspaceEpoch` 重挂载画布，重放刷新恢复路径
  （布局 + 相机逐像素还原）。入口：导出菜单「工作区存档」+ 导入对话框
  （按内容识别，非 .erreview 扩展名也认）。主题等个人偏好不随存档覆盖。
- **备注**：sessionStorage 不落盘的安全设计不变——存档是用户显式动作。

### 1.2 Schema 版本对比（diff）—— DB Refactor 的本命需求

- **价值**：评审的本质是审"变更"。导入"重构前/后"两份 DDL，直接看到表/字段/类型/
  索引/关系的增删改，工具从"看现状"升级为"审演进"。
- **做法**：
  1. 纯函数 `diffSchemas(before, after)` → 结构化差异（表级增删、字段级增删改
     〔类型/可空/默认值/注释〕、索引与外键变化）；
  2. 画布高亮：新增绿边框/删除红置灰/修改琥珀，字段行级 diff 标记；
  3. 差异报告导出（Markdown，与评审报告同管线）。
- **工作量**：中-大（diff 纯函数中，画布呈现是大头）。**依赖**：1.1（对比会话的
  载入/保存体验依赖存档）。

### 1.3 评审结论回流生成整改 SQL

- **价值**：闭环从"发现问题"走到"给出修改"，评审产出可直接进变更流程。
- **做法**：从既有数据生成草稿脚本：确认的外键 → `ALTER TABLE ADD CONSTRAINT`
  （已有）；批注中的结构化建议（见 2.2）→ `CREATE INDEX` / `COMMENT ON` /
  `ALTER TABLE ... COMMENT` 模板；导出为「整改建议.sql」（全部带 `-- REVIEW:` 注释
  说明来源，人工确认后执行）。
- **工作量**：小-中。**依赖**：2.2 的结构化批注（自由文本难以生成 SQL）。

## 阶段二：评审半自动化（产品差异化所在）

### 2.1 内置规范检查（schema lint）

- **价值**：评审员从"逐字段找问题"变成"逐条确认问题"，效率数量级变化；
  也是与"只画图"的 ER 工具拉开差距的关键能力。
- **做法**：纯函数规则引擎 `lintSchema(schema, effectiveFks)`，首批规则：
  无主键表、外键列缺索引、缺注释（表/字段）、命名风格不一致（camel/snake 混用）、
  保留字作列名、超宽表（>N 列告警）、疑似冗余字段（同表近似名）、`VARCHAR` 超长/
  无长度。结果进侧栏「规范检查」区块（沿用推断面板的确认/忽略交互），
  可一键转为字段批注；报告导出带 lint 汇总。规则可开关（persisted）。
- **工作量**：中（规则引擎小，规则逐条累积）。**依赖**：无。

### 2.2 批注结构化（级别 + 状态）✅ 已完成（0.3.3）

- **实现**：`FieldNote` 扩展 `severity: 建议|警告|阻塞` 与 `status: 待处理|已采纳|不采纳`
  （向后兼容：旧字符串/旧对象升级为 建议/待处理）；气泡加级别快捷选择（状态行
  仅编辑已有批注时出现）；行标记点按级别着色；评审浮层 待处理优先 排序 + 分级
  计数 + 状态徽章点击流转（不改写「写于」时间戳）；报告按级别分组、行首状态、
  级别×状态汇总行。1.3（整改 SQL 回流）的前置就绪。

## 阶段三：融入团队文档流

### 3.1 Mermaid / dbml 导出

- **价值**：评审结果进 Markdown（Mermaid `erDiagram`）与 dbdiagram.io（dbml）生态。
- **做法**：纯文本序列化（`exports/toMermaid.ts`、`toDbml.ts`），数据源与说明文档
  相同（visibleSchema + 已确认关系）。**工作量**：小-中。

### 3.2 报告 / 说明文档模板化

- **价值**：各团队有自己的文档规范；模板化避免"导出后手工重排"。
- **做法**：章节开关 + 自定义抬头（项目名/评审人/版本号）起步；
  后续可考虑简单模板变量。**工作量**：小起步。

### 3.3 只读分享（可选）

- **做法**：小 schema 用 URL hash 压缩编码；大 schema 依赖 1.1 的存档文件。
  纯前端约束下不做服务端。**工作量**：中。

## 阶段四：地基补齐（支撑以上一切）

### 4.1 解析器缺口（正确性优先级）

| 项 | 现状 | 严重度 |
| --- | --- | --- |
| `ALTER TABLE ... ADD COLUMN` | 列被静默丢弃，图结构性缺失 | **高（画出来就是错的）** |
| PG `COMMENT ON TABLE/COLUMN` | 仅告警，注释全丢（PG 用户主要注释方式） | 高 |
| 跨 schema 同名表 | `byName` 以裸表名为 key，互相串扰 | 高 |
| ENUM/SET 取值、CHECK 约束 | 静默压扁/丢弃 | 中 |
| PG 数组类型、`MODIFY/CHANGE COLUMN` | 不识别 | 中低 |

详见 [docs/SQL_PARSER.md](docs/SQL_PARSER.md) §四。

### 4.2 大库体验与工程化

- 解析/推断管线移入 **Web Worker** + 表数/输入长度阈值提示（当前几百表会冻结主线程）；
- **minimap** 与按模块聚焦视图（只看某个域）；
- 组件测试能力（vitest jsdom + `.test.tsx`）与 1-2 条 Playwright 冒烟进 CI；
- lint 把关（CI `--max-warnings 0`）、pre-commit hook、覆盖率采集。

### 4.3 既有布线债务（原 TODO-fix-bugs 已删除，唯一有效残留并入此处）

- ~~路由统一~~ —— **已决定不做**（2026-07-11）：导出与画布本就同源
  （都读 `routePoints`），双路径各有分工（静态走 dagre 通道、交互走实时绕行）。
  注意事项：布线改进默认只落在实时路径，静态首布局若再现贴边/穿卡再单独处理。
- side-bracket 泛化：紧贴并排（`gapX` 小正值）且端口垂直偏移大的卡片目前落到
  detour 而非更整洁的侧括号——因 `buildObstacles` 无法把端点卡片纳入穿越检测，
  用 gap 符号判断作为权宜。修复方向：`buildObstacles` 可选纳入端点卡片本体
  （扣掉端口所在行）。

## 推荐执行顺序

```
4.1 解析缺口  →  2.1 schema lint  →  1.2 版本 diff  →  1.3 整改 SQL 回流
      ↘  4.2 大库体验与工程化可并行
3.x 文档流集成（模板化、Mermaid/DBML，按团队需求插入）
4.3 布线债务（只处理有明确复现和收益的项目）
```

理由：当前版本已经解决存档和结构化批注，下一阶段应优先消除解析正确性风险，
再把规范检查和版本 diff 接到已有评审/报告管线上；大库体验和 E2E 则作为发布质量护栏持续补齐。
