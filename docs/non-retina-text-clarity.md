# 非 Retina 字体清晰度排查与修复

日期：2026-09-11。修复前基线：`1901426`（0.3.6，已包含空工作区引导）。

## 原因与证据

表名、字段和注释由 `TableOverlay` 内的 HTML 文本绘制，Cytoscape 负责图形与模型几何。文字本身没有跟随画布执行 CSS `scale()`，所以提高 Cytoscape canvas 的像素比不能修复这批 HTML 文本。

性能优化后，表格根元素同时使用 `translate3d(x, y, 0)` 和常驻的 `will-change: transform`。Cytoscape 返回的小数屏幕坐标直接用于该变换。实际示例的表格原点包括 `(67.3012, 494.138)`、`(396.904, 205.391)`；DPR=1 时，这些位置不对齐物理像素。

在同一 Chromium、同样文字、字号和尺寸下进行四组对照：小数坐标 + 3D、整数坐标 + 3D、小数坐标 + 2D、整数坐标 + 2D。DPR=1 截图中，常驻 3D 图层的文字明显柔化，仅修改其坐标不能充分恢复清晰度；去掉图层提升并使用 2D 定位后，字形边缘恢复清晰。DPR=2 也做了对照。

两个真实生产版本中，再使用含中文注释的相同工作区直接滚动画布，未注入或改写产品样式。旧版滚动停止后的虚化最明显，修复后恢复清晰。截图保存在本机 `/tmp/er-font-dpr1-before-scrolled.png`、`/tmp/er-font-dpr1-after-scrolled.png`；对应的 DPR=2 文件使用 `dpr2` 前缀。

这与浏览器将合成层绘制为位图后再变换的机制一致。Chrome 的[合成架构说明](https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/)和[重栅格化说明](https://developer.chrome.com/blog/re-rastering-composite)解释了图层缓存与 `will-change` 对绘制的影响；后者讨论的是缩放机制，不能直接当作本项目发生文字缩放的证据。本次归因主要依据项目源码与实际截图对照。

## 实现

1. `TableOverlay` 与命令式几何更新共用 `overlayTransform`，使用 2D `translate`，移除常驻的 `will-change: transform`。
2. 仅对显示原点执行 `round(position * DPR) / DPR`。DPR=1 使用 1 CSS px，DPR=2 使用 0.5 CSS px，支持 1.25 等分数像素比。每轴最大偏移为半个物理像素。
3. 保留 rAF 合帧、表格内容 memo、只更新根元素几何的性能路径。仅在尺寸真的改变时写 width/height；相同物理像素内的微小移动不重复写样式。
4. 监听分辨率媒体查询，在窗口跨屏或浏览器缩放改变 DPR 后重新对齐；组件卸载时清理监听。无需重新打开存档。
5. 不修改字号、文本内容、模型坐标、连线模型或工作区格式。吸附只影响最终绘制位置，不进入 sessionStorage、历史记录或 `.erreview`。

## 验证方式

- 单元测试覆盖普通屏幕、分数 DPR、Retina、负坐标、DPR 改变、模型精度保留，以及平移时不重复写尺寸。
- 浏览器回归覆盖 DPR=1/1.25/2 的存档恢复、双轴滚动、缩放、刷新及跨屏像素比切换；复用已有拖表、拖列、连线、对齐和 FPS 测试。
- 修复前后使用各自的生产构建、相同 Chromium 和 1440×1000 视口。每个规模预热 1 次、正式采样 5 次，每个动作 48 步、步间隔 8 ms；性能脚本确认移动真实发生。
- `perf/benchmark.mjs` 新增 `PERF_DEVICE_SCALE_FACTOR` 参数，默认 1，并将像素比记入报告，便于重复比较不同屏幕密度。

## 验证结果

359 个单元测试通过。20 个浏览器场景通过（首次全量 19 个通过；跨屏场景的 CDP 模拟修正后，4 个新增密度场景全部复测通过）。普通生产构建、单 HTML 构建和类型检查通过；lint 为 0 错误、7 个原有警告。

另外直接通过 `file://` 打开单 HTML 发行文件，加载 14 张表示例并滚动画布：所有表的显示原点对齐，常驻图层提示已移除，HTTP 请求为 0、页面错误为 0。

跨屏测试需要特别处理：CDP 的设备参数覆盖会更新 `devicePixelRatio`，但单独调用时不发出分辨率媒体查询的 change 事件。测试刷新了媒体模拟配置，让浏览器派发该事件；产品监听逻辑无需为模拟器增加轮询。

## 限制

自动化使用浏览器 DPR 模拟与本机截图，不能代替每一种真实显示器、操作系统字体栅格器及显卡组合。系统级显示缩放或浏览器自身的字体问题仍需在受影响设备复核。DPR=1 的物理分辨率本身也不会变成 Retina 的字形细节。

由于连线继续使用原始几何，像素吸附可能让表框与连线端点每轴相差至多半个物理像素；这是受控的显示差异，不会累计到模型或存档。
